# CH32V003 UART IAP Bootloader — Proteus32, Revision 2 (WL_FLASH-safe)

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)

UART-загрузчик для WCH CH32V003F4U6 (Proteus32). Принимает прошивку по USART1
на 460800 8N1 и записывает её в пользовательский flash с 0x08000000, **не
затрагивая область настроек WL_FLASH** (0x08003F00–0x08003FFF).

Спецификация полностью интегрирована в этот документ: исходное ТЗ v1.0
(2026-09-05, файл `BOOTLOADER_TZ.md`, удалён из репозитория в коммите `2610c37`)
перенесено ниже. Дополнений к ТЗ нет.

## Ключевые свойства (revision 2)

- **WL_FLASH неприкосновенен.** Загрузчик стирает/пишет только
  `[0x08000000, 0x08003F00)` (252 страницы × 64 Б). `FLASH_EraseAllPages()` (MER)
  удалён полностью; никакой записи/стирания в `0x08003F00..` не существует.
- **Никакой магии 0x5AA55AA5.** END-команда не выполняет операций с flash
  вообще (раньше стирала 4-ю страницу WL-кольца 0x08003FC0).
- **Структурные границы на стороне загрузчика:** PROM/VERIFY за пределами
  app-области отклоняются с `ERR_RANGE` (0x02) до любого обращения к flash;
  READ (0x84) читает весь user-flash (включая WL) только на чтение.
- **Полноценный VERIFY:** хост передаёт эталонные данные (кадр 0x82 с 64 Б);
  загрузчик сравнивает с flash и возвращает `ERR_VERIFY` (0x03) при несовпадении.
- **Сброс состояния сессии** при ERASE/END — оборванная сессия не «протекает»
  в следующую.
- Размер: **1680 Б** из 1920 Б boot-области (цель ТЗ ≤ 1888 Б, предел 1920 Б),
  контроль — size-гейтом в `build.cmd`.
- Индикация (P2): при входе в загрузчик мигает только красный (PC7, ~4 Гц,
  актив-высокий); зелёный (PC4) загорается с первым кадром обмена (ERASE)
  и горит до END; перед сбросом в приложение оба гаснут.

## Контекст и обоснование (ТЗ §1)

Ревизия 2 — хирургическая модификация рабочего каркаса (фрейминг `AA 55 … 55 AA`,
stop-and-wait, fast-program 64 Б), а не переписывание: при бюджете 1920 Б
переписывание даёт риск регрессий без выигрыша. Устранённые дефекты v1:

| # | Дефект v1 | Решение в v2 |
|---|---|---|
| P1 | ERASE = `FLASH_EraseAllPages()` (MER) стирал WL_FLASH → сброс всех настроек пользователя | постраничный fast-erase только `[0x08000000, 0x08003F00)` |
| P2 | END стирал страницу `0x08003FC0` (слоты 10–12 WL-кольца) и писал магию `0x5AA55AA5` в `0x08003FFC` | END без операций с flash; `CalAddr`/`CheckNum` удалены |
| P3 | нет границ записи/стирания на стороне загрузчика (только `MAX_FLASH_SIZE` в скрипте) | guard'ы PROM/VERIFY → `ERR_RANGE` до любого write/erase |
| P4 | VERIFY в скрипте — no-op (Len=0, сравнение 0 байт) | VERIFY передаёт 64 Б эталона, загрузчик сравнивает |
| P5 | ERASE не сбрасывал `Program_addr`/`Verify_addr`/`CodeLen` — оборванная сессия повреждала образ | сброс состояния сессии в ERASE/END |
| P6 | сборка невоспроизводима вне IDE (нет Makefile/SDK-заголовков) | `build.cmd` + vendored `SDK_inc/` + size-гейт |

Критерии успеха: WL-область побайтно идентична до/после любого числа обновлений;
`0x5AA55AA5` нигде не записывается; полный цикл стабилен; размер ≤ 1920 Б
(цель ≤ 1888 Б); сборка одной командой.

## Аппаратные ограничения и карта памяти (ТЗ §2)

МК: CH32V003F4U6 — RISC-V RV32EC, 24 МГц HSI (без PLL), 2 КБ SRAM, 16 КБ
пользовательского code flash + отдельная boot-область 1920 Б; гранула стирания
в fast-режиме — 64 Б (стандартный PER — 1 КБ, **запрещён**: не позволяет
не задеть 0x08003F00+).

Boot-область CH32V003 (0x00000000, 1920 Б) — **отдельная физическая область
flash, не входящая в 16 КБ пользовательского кода**. В BOOT-старте по 0x0
отображена она; в USER-старте по 0x0 алиасируется пользовательский flash
(0x08000000). Поэтому приложение (`ORIGIN = 0x0` = 0x08000000 в USER-режиме)
**не пересекается** с загрузчиком и не требует перелинковки; MER/PER
пользовательской области boot-область не затрагивает.

### Карта памяти (адреса точные, пересечения исключены)

| Область | Адреса | Размер | Режим доступа | Примечание |
|---|---|---|---|---|
| **Boot area (загрузчик)** | 0x00000000–0x0000077F | 1920 Б | маппится по 0x0 только в BOOT-старте; в USER-старте по 0x0 алиас user-flash | отдельная физическая flash; прошивается один раз через WCH-Link; MER/PER её не стирают |
| — код загрузчика | 0x00000000–0x0000068F | 1680 Б (факт после сборки) | — | бюджет кода: предел 1920 Б, цель ≤ 1888 Б |
| — служебная страница | 0x000007C0–0x000007FF | 64 Б | — | зарезервирована, не используется |
| **User code alias** | 0x00000000–0x00003EFF | зеркало 0x08000000 | USER-старт | по нему слинковано приложение (`ORIGIN = 0x0`, `FLASH_SIZE=16128`) |
| **Пользовательский code flash** | 0x08000000–0x08003FFF | 16384 Б | всегда | 256 страниц × 64 Б |
| — приложение | 0x08000000–0x08003EFF | 16128 Б (0x3F00) | чтение/запись/стирание | **единственная область записи загрузчика** |
| — **WL_FLASH (настройки)** | 0x08003F00–0x08003FFF | 256 Б (0x100) | **только чтение из загрузчика; запись/стирание ЗАПРЕЩЕНЫ** | 4 страницы × 64 Б: 0x08003F00, 0x08003F40, 0x08003F80, 0x08003FC0 |
| **Option Bytes** | 0x1FFFF800–0x1FFFF81F | — | — | стандартные 0x1FFFF800–0x1FFFF80B (RDPR/USER/Data0/Data1/WRPR0/WRPR1); данные приложения с шагом 2 Б: magic 0x1FFFF810, tc 0x1FFFF812, vc 0x1FFFF814, ml 0x1FFFF816. Загрузчиком не трогаются |
| **SRAM** | 0x20000000–0x200007FF | 2048 Б | — | у загрузчика: стек 256 Б + буферы |

Границы выровнены по странице 64 Б: `0x08003F00 = 252 × 0x40`, приложение —
ровно 252 страницы.

### Структура WL-области (цена ошибки)

Кольцо из 12 записей по 20 Б: заголовок (seq+version) + payload `app_cfg_t`
13 Б + CRC-16; 3 записи на 64-Б страницу (60 Б + 4 Б padding). Записи
размещаются с началом страницы: `0x08003FC0`, `0x08003FD4`, `0x08003FE8`.
`wl_load()` валидирует CRC/seq; пустое/повреждённое кольцо → `wl_init() +
ee_defaults()` → **все настройки пользователя сбрасываются к заводским**.
Именно поэтому стирание страницы 0x08003FC0 (END v1) уничтожало записи 10–12,
а `0x5AA55AA5` по 0x08003FFC формально попадал в padding, но вредил косвенно.

### Режимы старта

- **Power-on** — по Option Byte `USER` бит 5 (`OB_PowerON_Start_Mode_BOOT=0x0020`):
  BOOT → старт с 0x00000000 (загрузчик), USER → старт с 0x08000000 (приложение).
  Требуемое состояние — **BOOT** (заводское; так работает вход по кнопке;
  `ob_Flush()` приложения сохраняет этот бит).
- **System reset** — защёлка бит 14 `FLASH->STATR` (`SystemReset_StartMode`):
  `Start_Mode_USER` → старт с 0x08000000; `Start_Mode_BOOT` → с 0x00000000.

### Запрещённые операции (неукоснительно, ТЗ §2.4)

1. `FLASH_EraseAllPages()` (MER) — удалён из кода полностью, не вызывать ни при каких условиях.
2. Стандартное стирание PER (гранула 1 КБ) — запрещено: не позволяет не задеть 0x08003F00+.
3. Любая запись/стирание в `0x08003F00–0x08003FFF` (WL) — запрещены; чтение только командой READ.
4. Любые операции с Option Bytes (0x1FFFF800+, OPTER/OPTPG) из загрузчика — запрещены.
5. Запись/стирание boot-области из загрузчика — запрещены (и структурно невозможны:
   SDK-guards `ValidAddrStart..End = 0x08000000..0x08004000`; обход guards не добавлять).
6. Переконфигурация PD7 (SWIO) — запрещена: единственный канал аварийного
   восстановления через WCH-Link.
7. Исполнение flash-операций из пользовательской области — запрещено (весь код
   загрузчика исполняется из boot-области; `.highcode`-секция остаётся пустой).

## Вход в режим загрузчика (ТЗ §3.4)

- Питание при **зажатой кнопке** (PC3 прижата к GND) → `PC3_Check()` возвращает 0
  → IAP-режим, опрос UART. `PC3_Check` — внутренний pull-up (nibble3 = 0x8,
  `BSHR |= 1<<3`) и двойное чтение; без изменений.
- Питание без кнопки → `IAP_2_APP()` (`RCC_ClearFlag()`,
  `SystemReset_StartMode(Start_Mode_USER)`, `NVIC_SystemReset()`) → старт
  приложения с 0x08000000 (полный «холодный» старт: свой `handle_reset`,
  `SystemInit`, ремап векторов `mtvec = _start|3`; конфликтов с boot-областью нет).
- После команды END 0x83 загрузчик отвечает ACK, ждёт ≥100 мс (дрейн UART)
  и сбрасывается в приложение.
- Петля сброса исключена: после `IAP_2_APP()` при USER-старте загрузчик
  повторно не вызывается; `SystemReset_StartMode(Start_Mode_BOOT)` из ветвей
  запрещён.
- Поведение при отсутствии валидного приложения не специфицируется отдельно:
  boot-область всегда работоспособна, пользователь входит по кнопке повторно.

## Бюджет размера (ТЗ §3.1)

- Жёсткий предел — **1920 Б** (граница boot-области, hardware limit);
  целевой размер ≤ **1888 Б** (запас ≥ 32 Б). Факт: **1680 Б**.
- Сборка печатает размер и **падает с ошибкой** при превышении бюджета
  (size-гейт в `build.cmd`).
- Порядок урезания при переполнении (строго в этом порядке): (1) команда READ
  0x84; (2) гранулярные коды статусов (оставить 0x00/0x01); (3) инлайн
  `UART1_SendMultiyData`; (4) хвостовой padding-код VERIFY.
  **Урезанию не подлежат:** ограниченный ERASE, guards диапазонов, чистка END.

## Протокол UART (v2, ТЗ §3.5)

Физика: USART1, **460800 8N1**, no flow control, HSI 24 МГц (BRR = 0x34);
PD5 = TX (AF push-pull, CFGLR-нибл 0xB), PD6 = RX (input pull-up, нибл 0x8).
Stop-and-wait: следующий кадр — только после ответа на предыдущий (защита от
UART overrun во время стирания/записи страницы ~3–4 мс).

### Кадр запроса (host → bootloader)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | `0xAA` (SYNC1) |
| 1 | 1 | `0x55` (SYNC2) |
| 2 | 1 | CMD |
| 3 | 1 | LEN — длина PAYLOAD (ERASE/END = 0; PROM/VERIFY = 0x40; READ = 4) |
| 4 | LEN | PAYLOAD |
| 4+LEN | 2 | CHECKSUM, little-endian: сумма CMD + LEN + всех байтов PAYLOAD mod 0x10000 |
| 6+LEN | 1 | `0x55` (TAIL1) |
| 7+LEN | 1 | `0xAA` (TAIL2) |

### Команды

| CMD | Имя | LEN | PAYLOAD | Действие загрузчика |
|---|---|---|---|---|
| 0x80 | PROM | 0x40 | 64 Б данных | guard `Program_addr+64 ≤ 0x08003F00`; программирование 64-Б fast-записью (`CH32_IAP_Program`); `Program_addr += 0x40`; при отказе — ни одного байта, адрес не инкрементировать |
| 0x81 | ERASE | 0x00 (+4 Б addr, игнорируются) | — | `FLASH_Unlock_Fast()`; цикл `FLASH_ErasePage_Fast(a)` для `a = 0x08000000 … 0x08003EC0` шаг 64 (252 страницы); `FLASH_Lock_Fast()`; сброс состояния: `Program_addr = Verify_addr = 0x08000000`, `CodeLen = 0`, `Verify_Star_flag = 0` |
| 0x82 | VERIFY | 0x40 | 4 Б addr-заглушки + 64 Б эталона | guard `Verify_addr+64 ≤ 0x08003F00`; побайтное сравнение с flash; `Verify_addr += 0x40`; несовпадение → `ERR_VERIFY`, адрес не двигать |
| 0x83 | END | 0x00 | — (никаких дополнительных байт) | **Никаких операций с flash.** Ответ ACK, пауза ≥100 мс, `IAP_2_APP()` |
| 0x84 | READ | 0x04 | addr, uint32 LE | guard `0x08000000 ≤ addr && addr+64 ≤ 0x08004000` (весь user-flash, включая WL — только чтение); ответ с данными |
| прочее | — | — | — | ERR (0x01) |

4-байтовое адресное поле после LEN есть только у ERASE и VERIFY (заглушки,
парсер `UART_Rx_Deal` не менялся); `CMD_JUMP_IAP` (0x84 в старом коде) удалён.

### Кадр ответа (bootloader → host)

Базовый (все команды кроме успешного READ):

```
AA 55 00 ST 55 AA          # 6 байт; ST — статус
```

Успешный READ (единственный кадр с данными):

```
AA 55 84 00 <Data[64]> CKL CKH 55 AA   # 76 байт; CK = (0x84 + 0x00 + ΣData) mod 0x10000, LE
```

Коды статуса:

| ST | Значение | Когда |
|---|---|---|
| 0x00 | OK | команда выполнена |
| 0x01 | ERR | неизвестная команда, сбой flash (BSY-таймаут SDK) |
| 0x02 | ERR_RANGE | выход за [0x08000000, 0x08003F00) при записи/стирании |
| 0x03 | ERR_VERIFY | несовпадение данных при VERIFY |

Кадр с неверной контрольной суммой/хвостом — тихий отброс без ответа,
ресинк на `AA 55`. Между командами — строго stop-and-wait.

### Таймауты и повторы (ТЗ §3.5.5)

- Загрузчик: общего таймаута сессии нет (выход — END или питание). Базовая
  версия — блокирующее `Uart1_Rx()`: оборванный кадр может ждать байтов хостом;
  восстановление — новый полный кадр или переподключение (P2-улучшение:
  межбайтовый таймаут >500 мс → отброс недокадра).
- Хост: таймаут ответа 10 с для ERASE (252 × ~3–4 мс ≈ 1 с, запас), 3 с для
  остальных; 3 повтора с `reset_input_buffer()` между попытками; после
  исчерпания — аварийное завершение с кодом 1.

### Контрольные векторы (из ТЗ 3.5.4, байт-в-байт)

```
ERASE:   AA 55 81 00 00 00 00 08 89 00 55 AA          -> AA 55 00 00 55 AA
PROM:    AA 55 80 40 FF..FF(64) 80 40 55 AA           -> AA 55 00 00 55 AA
VERIFY:  AA 55 82 40 00 00 00 08 FF..FF(64) 8A 40 55 AA -> AA 55 00 00 55 AA
END:     AA 55 83 00 83 00 55 AA                      -> AA 55 00 00 55 AA
READ:    AA 55 84 04 00 3F 00 08 CF 00 55 AA          -> AA 55 84 00 <64 Б> CK 55 AA
Overflow:                                             -> AA 55 00 02 55 AA
```

### Обработка ошибок (ТЗ §3.6)

- Неверная CK/хвост → тихий отброс, ресинк на `AA 55`.
- Неизвестная команда → `ST=0x01`.
- Нарушение границ → `ST=0x02`, guard **до** любого write/erase (частичного
  выполнения нет).
- Несовпадение VERIFY → `ST=0x03`.
- Таймаут BSY в flash-операциях → `ST=0x01`.

## PC-скрипт (`proteus32_3.py`, v2.1, ТЗ §4)

Единый CLI-инструмент обновления и диагностики. Python 3.8+; зависимости
`pyserial`, `tqdm` (опционально, с деградацией прогресса). Коды выхода:
0 — успех, 1 — любая ошибка.

```
python proteus32_3.py <port> <firmware.bin> [-b 460800] [--no-verify]   # полный цикл
python proteus32_3.py <port> --erase-only                              # стирание app-области
python proteus32_3.py <port> --dump <file> --addr 0x08000000 --len 256 # чтение (READ 0x84)
python proteus32_3.py <port> --go                                      # запуск приложения (END)
python proteus32_3.py --version
```

- `<firmware.bin>` — сырой бинарник с `ORIGIN 0x08000000`; образ паддится 0xFF
  до кратности 64 Б. Размер ≤ 16128 Б (0x3F00) без исключений — флаг `--force`
  удалён (граница теперь структурная).
- Поток write: ERASE (таймаут 10 с, `ST≠0x00` → аварийный выход с расшифровкой
  кода) → PROM блоками 64 Б (3 с, tqdm) → VERIFY передачей того же паддированного
  образа (`ST=0x03` → отчёт со смещением блока, выход 1) → END (ответ может не
  прийти из-за сброса чипа — не ошибка) → итог: elapsed, KiB/s.
- Диагностика: `SerialException` → человекочитаемое сообщение; расшифровка ST
  (0x02 = «нарушение границ app-области (защита WL)»); после 3 неудачных попыток
  — подсказка про IAP-режим (питание при зажатой кнопке), проводку PD5/PD6 и
  скорость.
- Совместимость: скрипт v2.1 работает **только** с загрузчиком данной ревизии;
  пару «загрузчик + скрипт» поставлять вместе; в шапке скрипта —
  `PROTOCOL_REV = 2`. `flash_tool.cmd` совместим; пересборка
  `dist\Proteus32Flasher.exe` — через `build_exe.cmd`.

## Сборка

ОДНА команда (воспроизводимо):

```
build.cmd            # компиляция + линковка + size-гейт
build.cmd clean      # очистка build\
```

Требования: GCC riscv (MounRiver Studio 2: `riscv-wch-elf` (GCC 12)
или `riscv32-wch-elf` (GCC 15); fallback `riscv-none-embed` в PATH).
Скрипт ищет тулчейн в стандартных путях MounRiver; переопределение:
`set RISCV_GCC_BIN=C:\path\to\RISC-V Embedded GCC\bin`.

Флаги: `-march=rv32ecxw -mabi=ilp32e -Os -ffunction-sections -fdata-sections
-nostartfiles -flto -Wall -T Ld/Link.ld --specs=nano.specs --specs=nosys.specs
-Wl,--gc-sections`.

Артефакты: `build/bootloader.bin` (сырой образ boot-области, 0x00000000),
`build/bootloader.elf` (отладка), `build/bootloader.map`.

SDK: заголовки — `SDK_inc/` (skopированы из framework-wch-noneos-sdk,
vendored), исходники — `SDK_src/` (только используемые: flash, rcc, usart).

**Прошивка загрузчика** — только через WCH-Link (SWD/библиотека MounRiver),
в boot-область по 0x00000000.

Size-гейт: падение при >1920 Б, предупреждение при >1888 Б. Текущий размер
выводится при каждой сборке.

## Ограничения и допущения (ТЗ §7)

- Загрузчик не мешает приложению: при каждом включении — только проход
  boot-области (<1 мс); PD5/PD6/PC3 переконфигурируются приложением при старте.
- Самообновление загрузчика (dual-bank) — вне объёма; boot-область обновляется
  только WCH-Link'ом.
- Программный вход в обновление из приложения — вне объёма (P2-направление).
- Протокол без аутентификации/шифрования: физический доступ к UART = полный контроль.
- Stop-and-wait обязателен; однопроходная модель (одна область приложения,
  без dual-bank/отката); аварийное восстановление — постоянство boot-области
  и вход по кнопке.
- Износ flash: ERASE стирает 252 страницы за цикл; при ресурсе ≥10 тыс. циклов
  на страницу деградация несущественна.
- Скорость и формат зафиксированы: 460800 8N1, HSI 24 МГц; изменение SYSCLK
  сломает BRR — при смене тактирования пересобирать загрузчик.

## Несовместимость версий

- Скрипт v2.1 (`proteus32_3.py`) поставляется в двух копиях (этот репозиторий
  и `BootUI`) и обязан оставаться в синхронизации по протокольной части.
  Реальная история: обе копии при поставке с загрузчиком содержали баг
  разбора READ-кадра (ожидались 74 Б вместо фактических 72), из-за которого
  `--dump` не работал; исправление (72/76-байтовый разбор, probe ревизии
  протокола перед ERASE/END) внесено централизованно в `BootUI` и
  синхронизировано в этот репозиторий. Ранее упоминавшийся здесь VERIFY
  с Len=0 (no-op) у текущих скриптов отсутствует — VERIFY передаёт реальные
  64 Б эталона, несовместимости с протоколом v2 нет.
- Старый загрузчик (v1): VERIFY-no-op, READ отсутствует, END стирал
  0x08003FC0 и писал магию 0x5AA55AA5. Пару не смешивать с v2.
