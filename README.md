# Proteus32 UART IAP Bootloader (CH32V003, Protocol Rev 2)

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
![MCU](https://img.shields.io/badge/MCU-CH32V003F4U6-blue)
![Protocol](https://img.shields.io/badge/Protocol-Rev%202%20(WL__FLASH--safe)-success)
![Size](https://img.shields.io/badge/Size-1680%20%2F%201920%20B-informational)

Компактный и безопасный UART-загрузчик (In-Application Programming) для микроконтроллера **WCH CH32V003F4U6** (проект Proteus32). Размещается в выделенной системной области загрузчика (`1920 Б`), принимает прошивку по `USART1` на скорости **460800 бод (8N1)** и записывает её в пользовательскую Flash-память с адреса `0x08000000`, **гарантированно сохраняя нетронутой область пользовательских настроек `WL_FLASH` (`0x08003F00–0x08003FFF`)**.

Для работы с загрузчиком на ПК предусмотрены:
* **Графическая оболочка (GUI):** [BootUI (Proteus 32 Flasher)](https://github.com/tama18101971/BootUI) — современное приложение в стиле Windows 11 Fluent Design.
* **Консольная утилита (CLI):** скрипт `proteus32_3.py` (входит в состав обоих репозиториев).

## Ключевые особенности Revision 2

* **Неприкосновенность `WL_FLASH`:** загрузчик стирает и программирует строго диапазон приложения `[0x08000000, 0x08003F00)` (252 страницы по 64 байта = `16 128 Б`). Массовое стирание `FLASH_EraseAllPages()` (`MER`) и килобитное стирание (`PER`) полностью исключены из кода.
* **Отказ от магического слова в Flash:** команда завершения `END` (`0x83`) больше не стирает последнюю страницу Flash и не записывает константу `0x5AA55AA5` по адресу `0x08003FFC` (что в ревизии 1 разрушало кольцевой буфер настроек).
* **Аппаратно-программные барьеры (Guards):** любые попытки записи (`PROM`) или верификации (`VERIFY`) за пределами `0x08003F00` блокируются загрузчиком до обращения к контроллеру Flash с возвратом статуса `ERR_RANGE` (`0x02`).
* **Полноценная верификация (`VERIFY`):** хост передает 64-байтные блоки эталонного образа, а загрузчик побайтно сверяет их с содержимым Flash, возвращая `ERR_VERIFY` (`0x03`) при малейшем расхождении.
* **Диагностическое чтение (`READ`):** команда `0x84` позволяет безопасно считывать любые 64-байтные страницы всего пользовательского Flash `[0x08000000, 0x08004000)`, включая область `WL_FLASH`, а также используется клиентами для автоматической проверки версии загрузчика (Protocol Probe) перед стиранием.
* **Изоляция сессий:** команды `ERASE` и `END` принудительно сбрасывают внутренние указатели (`Program_addr`, `Verify_addr`, `CodeLen`), предотвращая повреждение прошивки после прерванной передачи.
* **Строгий контроль размера:** бинарный образ занимает **1680 байт** при целевом бюджете `<= 1888 Б` и аппаратном потолке boot-области `1920 Б`.

## Аппаратная конфигурация и индикация

* **Микроконтроллер:** WCH CH32V003F4U6 (ядро RISC-V RV32EC).
* **Тактирование:** внутренний генератор `HSI 24 МГц` (без PLL, `HCLK = SYSCLK = 24 МГц`, 0 wait states).
* **Интерфейс UART:** `USART1`, скорость **460800 бод** (`USART1->BRR = 0x34`), формат **8N1**, без аппаратного управления потоком.

### Назначение выводов (Pinout)

| Вывод | Режим в загрузчике | Назначение |
| :--- | :--- | :--- |
| **PC3** | Input Pull-Up (`CFGLR nibble = 0x8`, `BSHR = 1<<3`) | Кнопка входа в режим загрузчика (активный уровень — **LOW / GND**) |
| **PD5** | Alternate Function Push-Pull (`0xB`) | `USART1_TX` — передача данных от МК к ПК |
| **PD6** | Input Pull-Up (`0x8`) | `USART1_RX` — приём данных от ПК |
| **PC7** | Output Push-Pull 30 MHz (`0x3`) | Красный светодиод — индикация активности загрузчика (мигание **~4 Гц**) |
| **PC4** | Output Push-Pull 30 MHz (`0x3`) | Зелёный светодиод — индикация процесса приёма/прошивки данных |
| **PD7** | Штатный `SWIO` (не перенастраивается) | Однопроводной интерфейс отладки и аварийного восстановления через WCH-Link |

## Карта памяти и защита WL_FLASH

Область загрузчика (`Boot Area`, `1920 Б`) в CH32V003 является **физически отдельной** флеш-памятью и не отнимает место у 16 КБ пользовательской памяти.
* При старте в режиме **BOOT** по адресу `0x00000000` отображается область загрузчика.
* При старте в режиме **USER** по адресу `0x00000000` отображается зеркало пользовательской памяти (`0x08000000`), благодаря чему основное приложение компонуется со стандартным `ORIGIN = 0x00000000` без сдвига векторов прерываний.

| Область памяти | Диапазон адресов | Размер | Права загрузчика | Описание |
| :--- | :--- | :--- | :--- | :--- |
| **Boot Area** | `0x00000000 – 0x0000077F` | 1920 Б | Только исполнение | Системная область загрузчика (30 страниц по 64 Б). Прошивается через WCH-Link. Код занимает `0x00000000–0x0000068F` (1680 Б). |
| **Reserved** | `0x000007C0 – 0x000007FF` | 64 Б | Не используется | Служебная зарезервированная страница. |
| **User Code Alias** | `0x00000000 – 0x00003EFF` | 16 128 Б | — | Зеркало `0x08000000` при старте в режиме `USER`. |
| **App Area (Flash)** | `0x08000000 – 0x08003EFF` | **16 128 Б** (`0x3F00`) | **Чтение / Стирание / Запись** | **Единственная область записи загрузчика** (252 страницы по 64 Б). |
| **WL_FLASH (Настройки)** | `0x08003F00 – 0x08003FFF` | **256 Б** (`0x0100`) | **Только чтение (`READ`)** | 4 страницы по 64 Б (`0x3F00`, `0x3F40`, `0x3F80`, `0x3FC0`). Хранилище wear-leveling кольца настроек (12 слотов по 20 Б). Запись и стирание **строго запрещены**. |
| **Option Bytes** | `0x1FFFF800 – 0x1FFFF81F` | 32 Б | Не затрагиваются | Конфигурационные байты МК и калибровки приложения. |
| **SRAM** | `0x20000000 – 0x200007FF` | 2048 Б | Чтение / Запись | ОЗУ (стек загрузчика 256 Б + буферы приёма и программирования). |

## Логика старта и входа в загрузчик

Для работы загрузчика бит `OB_PowerON_Start_Mode` в Option Bytes (`USER` byte, бит 5) должен находиться в заводском состоянии **`BOOT`** (`0x0020`). При каждой подаче питания управление получает загрузчик по адресу `0x00000000`:

1. **Опрос кнопки (`PC3_Check`):** при старте настраивается внутренняя подтяжка вывода `PC3` к питанию и выполняется двойное чтение его состояния:
   * **`PC3 == HIGH` (кнопка отпущена):** загрузчик немедленно (`< 1 мс`) вызывает `IAP_2_APP()`, которая очищает флаги сброса (`RCC_ClearFlag()`), переключает защёлку режима старта в `Start_Mode_USER` (бит 14 `FLASH->STATR`) и выполняет программный сброс `NVIC_SystemReset()`. После этого МК запускает пользовательское приложение с `0x08000000` в штатном «холодном» состоянии.
   * **`PC3 == LOW` (кнопка зажата на GND):** загрузчик остаётся в режиме обновления (IAP), включает индикацию на `PC7` и переходит к непрерывному опросу `USART1`.
2. **Завершение обновления (`END`):** после приёма команды `0x83` загрузчик отправляет подтверждение `ACK`, гасит светодиоды, выдерживает паузу `~150–190 мс` (`END_DRAIN_DELAY`, не менее 100 мс для гарантированной отправки байтов по UART) и вызывает `IAP_2_APP()`.

## Спецификация протокола обмена (Rev 2)

Обмен ведётся по принципу **Stop-and-Wait** (полудуплексный запрос-ответ): хост отправляет следующий пакет только после получения ответа на предыдущий. Это исключает переполнение буфера `USART1` во время стирания или быстрой записи страницы Flash (`~3–4 мс`).

### 1. Структура пакета запроса (Host → Bootloader)

Все пакеты обрамляются стартовой сигнатурой `AA 55` и хвостовой сигнатурой `55 AA`. Контрольная сумма (`CHECKSUM`) представляет собой **16-битную сумму без знака по модулю `0x10000`** всех байтов между стартовой и хвостовой сигнатурами (включая `CMD`, `LEN`, опциональное поле `ADDR_STUB` и все байты `DATA`), передаваемую в формате **Little-Endian** (младший байт первый).

```text
+-------+-------+-------+-------+---------------+-------------+-------+-------+-------+-------+
| SYNC1 | SYNC2 |  CMD  |  LEN  |   ADDR_STUB   |   DATA...   |  CKL  |  CKH  | TAIL1 | TAIL2 |
| 0xAA  | 0x55  | 1 Б   | 1 Б   | 0 или 4 байта | 0..64 байт  | 1 Б   | 1 Б   | 0x55  | 0xAA  |
+-------+-------+-------+-------+---------------+-------------+-------+-------+-------+-------+
                 \______________________ _____________________/
                                        V
                     CHECKSUM = sum(bytes) mod 0x10000 (LE)
```

> **Особенность парсера (`UART_Rx_Deal`):** для обратной совместимости структуры буфера команды **`ERASE` (`0x81`)** и **`VERIFY` (`0x82`)** содержат 4-байтовое поле адреса-заглушки (`ADDR_STUB`, Little-Endian) сразу после байта `LEN`. Эти 4 байта не входят в значение `LEN`, но **обязательно входят в расчёт контрольной суммы**. У команд `PROM` (`0x80`), `END` (`0x83`) и `READ` (`0x84`) поле `ADDR_STUB` отсутствует.

### 2. Таблица команд

| Код (`CMD`) | Команда | `LEN` | `ADDR_STUB` | `DATA` (`LEN` байт) | Полный размер кадра | Действие загрузчика |
| :---: | :--- | :---: | :---: | :--- | :---: | :--- |
| **`0x80`** | `PROM` | `0x40` (64) | Нет | 64 Б прошивки | **72 Б** | Проверяет `Program_addr + 64 <= 0x08003F00`. Разблокирует fast-режим, записывает 64-байтную страницу (`CH32_IAP_Program`), увеличивает `Program_addr += 0x40`. |
| **`0x81`** | `ERASE` | `0x00` (0) | 4 Б (игнор.) | Нет | **12 Б** | Постранично стирает 252 страницы `[0x08000000, 0x08003F00)` через `FLASH_ErasePage_Fast`. Сбрасывает `Program_addr = Verify_addr = 0x08000000`, `CodeLen = 0`. |
| **`0x82`** | `VERIFY` | `0x40` (64) | 4 Б (игнор.) | 64 Б эталона | **76 Б** | Проверяет `Verify_addr + 64 <= 0x08003F00`. Сравнивает 64 Б с Flash по `Verify_addr`. При успехе сдвигает `Verify_addr += 64`; при ошибке возвращает `ERR_VERIFY` без сдвига адреса. |
| **`0x83`** | `END` | `0x00` (0) | Нет | Нет | **8 Б** | Сбрасывает состояние сессии, устанавливает `End_Flag = 1`, отправляет `ACK`, ждёт `>= 100 мс` и перезагружает МК в приложение (`IAP_2_APP`). |
| **`0x84`** | `READ` | `0x04` (4) | Нет | 4 Б адреса (`u32 LE`) | **12 Б** | Проверяет `0x08000000 <= addr` и `addr + 64 <= 0x08004000`. Читает 64 Б из Flash и возвращает кадр данных `READ`. |

### 3. Структура пакетов ответа (Bootloader → Host)

#### Базовый ответ (6 байт) — для `PROM`, `ERASE`, `VERIFY`, `END` и при любых ошибках:

```text
+-------+-------+-------+-------+-------+-------+
| 0xAA  | 0x55  | 0x00  |  ST   | 0x55  | 0xAA  |
+-------+-------+-------+-------+-------+-------+
```

* Байт `[2]` всегда равен `0x00`.
* Байт `[3]` (`ST`) содержит код статуса выполнения:

| Код `ST` | Константа | Описание |
| :---: | :--- | :--- |
| **`0x00`** | `ERR_SUCCESS` (`ST_OK`) | Команда успешно выполнена (`ACK`). |
| **`0x01`** | `ERR_ERROR` (`ST_ERR`) | Неизвестный код команды или аппаратный сбой. |
| **`0x02`** | `ERR_RANGE` (`ST_ERR_RANGE`) | Попытка выхода за пределы допустимой области памяти (сработала защита `WL_FLASH`). |
| **`0x03`** | `ERR_VERIFY` (`ST_ERR_VERIFY`) | Расхождение данных при побайтной сверке в команде `VERIFY`. |

#### Ответ с данными на успешный `READ` (72 байта):

```text
+-------+-------+-------+-------+----------------+-------+-------+-------+-------+
| 0xAA  | 0x55  | 0x84  | 0x00  |   Data[64]     |  CKL  |  CKH  | 0x55  | 0xAA  |
+-------+-------+-------+-------+----------------+-------+-------+-------+-------+
|  [0]  |  [1]  |  [2]  |  [3]  |   [4 .. 67]    | [68]  | [69]  | [70]  | [71]  |
```

* Контрольная сумма ответа: `CK = (0x84 + 0x00 + sum(Data[0..63])) mod 0x10000` в формате Little-Endian.

### 4. Эталонные контрольные векторы (Hex)

| Операция | Запрос (Host → Bootloader) | Ответ (Bootloader → Host) |
| :--- | :--- | :--- |
| **ERASE** | `AA 55 81 00 00 00 00 08 89 00 55 AA` | `AA 55 00 00 55 AA` |
| **PROM** (64×`0xFF`) | `AA 55 80 40 FF..FF(64) 80 40 55 AA` | `AA 55 00 00 55 AA` |
| **VERIFY** (64×`0xFF`) | `AA 55 82 40 00 00 00 08 FF..FF(64) 8A 40 55 AA` | `AA 55 00 00 55 AA` |
| **END** | `AA 55 83 00 83 00 55 AA` | `AA 55 00 00 55 AA` |
| **READ** (`0x08003F00`) | `AA 55 84 04 00 3F 00 08 CF 00 55 AA` | `AA 55 84 00 <64 Б> CKL CKH 55 AA` |
| **Выход за границы** | Запись/чтение вне разрешённого окна | `AA 55 00 02 55 AA` (`ERR_RANGE`) |

### 5. Таймауты, повторы и обработка сбоев

* **Битые кадры:** если при приёме не совпали стартовые/хвостовые байты или контрольная сумма, загрузчик молча отбрасывает пакет (не отправляя ответа) и ждёт следующей синхропоследовательности `AA 55`.
* **Политика повторов на хосте:**
  * Таймаут ожидания ответа на `ERASE` — **10.0 с** (реальное время стирания 252 страниц составляет `~1 с`).
  * Таймаут для `PROM`, `VERIFY`, `READ`, `END` — **3.0 с**.
  * При отсутствии ответа хост очищает входной буфер (`reset_input_buffer()`) и повторяет отправку пакета до **3 раз**. Если загрузчик явно вернул код ошибки (`0x01`, `0x02`, `0x03`), повторная отправка не производится.
* **Защита от старого загрузчика (`probe_protocol_v2`):** перед выполнением разрушающих команд (`ERASE` или `END`) клиенты отправляют пробный запрос `READ` (`0x84`) по адресу `0x08000000`. Так как команда `0x84` существует только в **Revision 2**, успешный 72-байтный ответ гарантирует, что на плате установлен безопасный загрузчик, который не сотрёт настройки `WL_FLASH`.

## Инструменты прошивки (GUI и CLI)

### 1. Графическая оболочка — [BootUI (Proteus 32 Flasher)](https://github.com/tama18101971/BootUI)

Для удобной работы без командной строки разработан графический клиент **[BootUI](https://github.com/tama18101971/BootUI)** (`bootloader_gui.py`):
* Современный интерфейс на базе **Windows 11 Fluent Design** (`sv-ttk`) с автоматическим определением системной тёмной/светлой темы и поддержкой экранов High-DPI.
* **Неразрушающая проверка связи («Проверить»):** опрашивает МК командой `READ` (`0x84`) и подтверждает наличие загрузчика `rev 2`.
* **Контроль размера прошивки:** наглядная шкала заполнения памяти (максимум `16 128 Б` / `15.75 КиБ`) и автоматическая блокировка файлов, угрожающих области `WL_FLASH`.
* **Неблокирующий процесс прошивки:** фоновый поток с поэтапной индикацией (`Проверка → Стирание → Запись → Верификация → Запуск`), отображением скорости (`КиБ/с`), кнопкой безопасной отмены и цветным журналом событий (с копированием и экспортом в `.txt`).

### 2. Консольный скрипт (`proteus32_3.py` v2.1)

В корне репозитория находится самодостаточный CLI-скрипт `proteus32_3.py` (Python 3.8+, зависимости: `pyserial`, опционально `tqdm` для прогресс-бара).

```bash
# Установка зависимостей
pip install pyserial tqdm

# Полный цикл: проверка rev 2 -> стирание -> запись -> верификация -> старт приложения
python proteus32_3.py COM5 firmware.bin

# Прошивка без этапа верификации
python proteus32_3.py COM5 firmware.bin --no-verify

# Только очистка области приложения (WL_FLASH не затрагивается) и перезапуск
python proteus32_3.py COM5 --erase-only

# Чтение (дамп) области памяти (например, дамп всех 256 байт настроек WL_FLASH)
python proteus32_3.py COM5 --dump wl_backup.bin --addr 0x08003F00 --len 256

# Выход из загрузчика и запуск основного приложения (отправка команды END)
python proteus32_3.py COM5 --go
```

> **Примечание:** бинарный файл прошивки автоматически дополняется байтами `0xFF` до размера, кратного 64 байтам. Код возврата скрипта: `0` — успешно, `1` — ошибка.

## Сборка проекта и прошивка загрузчика

Сборка полностью автоматизирована, не требует запуска IDE и выполняется одним пакетным файлом `build.cmd`. Заголовки и используемые модули драйверов (`flash`, `rcc`, `usart`) включены в репозиторий (`SDK_inc/`, `SDK_src/`).

### Требования к тулчейну
Компилятор **RISC-V Embedded GCC** (`riscv-wch-elf-gcc`, `riscv32-wch-elf-gcc` или `riscv-none-embed-gcc`) из состава MounRiver Studio 2 или прописанный в `PATH`. При нестандартном расположении укажите путь перед запуском:

```cmd
set "RISCV_GCC_BIN=C:\path\to\RISC-V Embedded GCC\bin"
```

### Команды сборки

```cmd
build.cmd          :: Полная пересборка + проверка лимита размера (size-gate)
build.cmd clean    :: Удаление каталога build\
```

* **Флаги компиляции:** `-march=rv32ecxw -mabi=ilp32e -Os -ffunction-sections -fdata-sections -nostartfiles -flto -Wall -T Ld/Link.ld --specs=nano.specs --specs=nosys.specs -Wl,--gc-sections`
* **Выходные артефакты:**
  * `build\bootloader.bin` — готовый бинарный образ для записи в Boot Area (`0x00000000`).
  * `build\bootloader.elf` — ELF-файл с символами отладки.
  * `build\bootloader.map` — карта компоновки.
* **Size-Gate:** скрипт сборки автоматически проверяет размер `bootloader.bin` (предупреждение при `> 1888 Б`, ошибка сборки при `> 1920 Б`).

### Прошивка самого загрузчика в МК
Загрузчик записывается в микроконтроллер **один раз** с помощью программатора **WCH-LinkE** (по линии `SWIO` / `PD7`) через утилиту **WCH-LinkUtility** или **MounRiver Studio** в системную область Boot Flash по базовому адресу **`0x00000000`** (Option Byte `PowerON_Start_Mode` должен быть установлен в `BOOT`).

## История изменений (v1 → v2)

| Проблема в v1 (исходный пример WCH) | Решение в v2.0.0 (Proteus32 WL_FLASH-safe) |
| :--- | :--- |
| Команда `ERASE` вызывала `FLASH_EraseAllPages()` (`MER`), уничтожая пользовательские настройки в `WL_FLASH` | Постраничное стирание `FLASH_ErasePage_Fast()` строго в границах `[0x08000000, 0x08003F00)` (252 страницы по 64 Б) |
| Команда `END` стирала страницу `0x08003FC0` и записывала `0x5AA55AA5` в `0x08003FFC`, ломая слоты 10–12 кольца настроек | Команда `END` не обращается к Flash вообще: отправляет `ACK`, ждёт дрейн UART и выполняет сброс в приложение |
| Отсутствие проверки границ записи внутри загрузчика | Жёсткие проверки диапазонов в `PROM`, `VERIFY`, `READ` с возвратом `ERR_RANGE` (`0x02`) до обращения к памяти |
| Команда `VERIFY` в клиентах работала вхолостую (`Len = 0`) | Передача 64 Б эталонных данных в `VERIFY` и реальное побайтное сравнение с возвратом `ERR_VERIFY` (`0x03`) |
| Оборванная сессия оставляла смещённые `Program_addr` и `CodeLen` | Сброс всех указателей сессии (`Session_Reset()`) при каждом вызове `ERASE` и `END` |
| Блокировка опроса `RXNE` логикой мигания светодиодов (падение скорости до 1 блока в 4 с) | Независимое обслуживание `USART_FLAG_RXNE` на каждой итерации главного цикла |
| Отсутствие команды чтения и способа отличить v1 от v2 | Добавлена команда `READ` (`0x84`), используемая для дампа памяти и защитной проверки ревизии протокола (`probe_protocol_v2`) |
